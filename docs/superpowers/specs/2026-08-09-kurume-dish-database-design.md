# 久留米市「料理の栄養価一覧」の取り込みと料理検索機能 設計書

日付: 2026-08-09

## 背景・目的

[2026-08-08-mext-food-database-design.md](2026-08-08-mext-food-database-design.md)で、文部科学省の日本食品標準成分表(生の食材・原材料が中心)を取り込み、食品管理画面から検索・登録できるようにした。

しかし「カレー」「親子丼」のような**完成した料理のメニュー名**で検索すると、成分表には該当する項目が少ない(「調理済み流通食品類」区分に55品目のみ)。今回、福岡県久留米市が公開しているオープンデータ「料理の栄養価一覧」を追加で取り込み、日常的な料理名(親子丼・カツ丼・牛丼・肉じゃが・から揚げ・うどん各種・みそ汁各種など286品目)からも栄養値を登録できるようにする。

### 探索の経緯(参考)

当初は「東京都オープンデータカタログサイト」「学校給食の献立表オープンデータ(川崎市・生駒市等)」を調査したが、いずれも「メニュー名」と「栄養値」が1対1で結びついた構造化データではなかった(学校給食データは日単位の合計カロリーのみで、個別料理ごとの数値がない)。範囲を広げて調査した結果、久留米市が公開する「料理の栄養価一覧」が、料理ごとにエネルギー・たんぱく質・脂質・炭水化物・食塩相当量の5項目をすべて含む、目的に合致したデータであることを確認した。

## スコープ

### 含める機能

- 久留米市公開のCSV(286品目)を、アプリ用JSONとObsidian閲覧用Markdownに変換する変換スクリプト
- 食品管理画面に、既存の「成分表から探す」(生の食材)とは別に「料理から探す」(完成した料理)の検索欄を新設
- 検索結果から選ぶと、栄養値がper100g換算されたうえで登録フォームに流し込まれる導線

### 含めない機能

- ExcelやCSVに含まれる「使用食材リスト」「野菜量」をアプリのUI上に表示すること(Markdown参考資料には残すが、アプリの登録フォームでは使わない)
- 「1人前」「1個」のような分量単位そのものをアプリに導入すること。既存の「per100gの値 × 入力g数」というデータモデルを維持し、久留米市データもper100gに換算してから使う(理由は後述)

## データソース

- 出典: 久留米市「料理の栄養価一覧」(久留米市保健所健康推進課)
- 公開元: [BODIK(ビッグデータ&オープンデータ・イニシアティブ九州)](https://data.bodik.jp/dataset/402036_0009100_00005)
- CSV直接URL: `https://data.bodik.jp/dataset/12425147-84ca-427e-b46f-8c3229536365/resource/adf887ae-101b-42ee-9a37-97fcdd25a620/download/40203691000000500001.csv`
- ライセンス: クリエイティブ・コモンズ 表示(CC BY)。「久留米市『料理の栄養価一覧』(CC BY)」の形でクレジット表記する。
- 形式: CSV(UTF-8 BOM付き)、71KB、287行(ヘッダ1行+料理286品目)、50列
- 文部科学省「日本食品標準成分表2010年版」を基に久留米市が算出したデータ

### CSVの構造

| 列 | 内容 |
|---|---|
| 0 | 料理の種類(例: ごはん、麺、肉料理＿焼き物・炒め物) |
| 1 | 料理名(例: 親子丼、かけうどん) |
| 2〜6 | エネルギー[kcal]・たんぱく質[g]・脂質[g]・炭水化物[g]・食塩相当量[g](**1人前あたり**) |
| 7 | 野菜量[g] |
| 8〜47 | 材料1〜20の「材料名」「重量[g]」のペア(未使用分は空文字) |

実データを検証済み: 全286行で列数は50に統一、5栄養素の欠損なし、材料重量の空文字以外の値はすべて数値としてパース可能、重複する料理名なし。

### per100g換算の方針

このCSVの栄養値は「ごはん(中茶碗1杯)」「牛乳(コップ1杯)」のように**1人前あたり**の値であり、既存アプリが前提とする「per100gの値」ではない。かといって「1人前」という新しい分量単位をアプリに追加すると、既存の食事記録フォーム(量をgで入力する前提)に影響が及び、変更範囲が大きくなる。

そこで、**その料理で使われている材料の重量(材料1〜20の合計g)で割ってper100gに逆算する**方針を採る。

```
per100g.kcal = round(1人前のエネルギー ÷ 材料重量の合計g × 100, 1)
```

たんぱく質・脂質・炭水化物・食塩相当量も同様に換算する。実データで検証済み:

| 料理名 | 1人前kcal | 材料重量合計 | 換算後per100g |
|---|---|---|---|
| ごはん(中茶碗1杯) | 252 | 150g | 168.0kcal |
| 牛乳(コップ1杯) | 101 | 150g | 67.3kcal |
| みかん(M1個) | 40 | 88g | 45.5kcal |
| 塩(1つまみ) | 0 | 1g | 0.0kcal |

いずれも実際の食品として妥当な値になることを確認した。全286行で材料重量の合計が0になる行は存在しない(ゼロ除算の心配はない)ことも確認済みだが、変換スクリプトでは念のため合計0の行を検出したらスキップし警告を出す(将来データが更新された場合の保険)。

### 料理名の扱い

久留米市データの料理名は「ごはん(中茶碗1杯)」のように、括弧内に分量の目安が入っているものが多い。これは元データの意味ある情報(どれくらいの量で何kcalか)なので、削らずそのまま候補一覧に表示する。登録時に短く言い換えたい場合は、既存の成分表機能と同様、フォームの食品名欄で自由に編集できる。

## 変換スクリプト

`tools/build_dish_database.py`(Python 3、標準ライブラリの`csv`のみで実装可能。xlsx変換のような`openpyxl`は不要)

### 入出力

- 入力: `tools/cache/kurume_dishes.csv`。存在しなければ上記URLから自動取得する。`tools/cache/`は既存の`.gitignore`で追跡対象外。
- 出力1: `data/kurume-dishes.json` — アプリが読む
- 出力2: `docs/料理/01_ごはん.md` 〜 `docs/料理/25_調味料.md` — 人が読む(料理の種類ごとに1ファイル、25ファイル)

久留米市データには文科省成分表のような公式の分類番号がないため、ファイル名の連番はCSV内で各カテゴリが最初に登場する順番(ごはん→パン→麺→肉料理＿焼き物・炒め物→…→調味料)をそのまま01から振る。この順番はCSVの行順に依存するため、元データの行順が変わらない限り再実行しても同じ番号になる。

### 出力JSONの形式

```json
[
  {
    "code": "K011",
    "group": "ごはん",
    "name": "親子丼",
    "per100g": { "kcal": 132.5, "protein": 5.7, "fat": 1.8, "carb": 22.1, "salt": 0.4 }
  }
]
```

`code`は久留米市データに固有IDがないため、変換スクリプトが料理の種類ごとの通し番号から`K001`形式で生成する(例: `K001`〜`K286`)。`js/foodForm.js`で登録済み食品と紐づける参照情報としてのみ使う。

`per100g`の各値は、上記の換算式で計算し小数第1位に丸める。

### 出力Markdownの形式

料理の種類ごとに1ファイル。1人前あたりの元の値・野菜量・材料リストも残し、per100gがどう算出されたか人が追えるようにする。

```markdown
# ごはん

出典: 久留米市「料理の栄養価一覧」(CC BY)
生成日: 2026-08-09 / 品目数: 18

栄養価は文部科学省「日本食品標準成分表2010年版」を基に久留米市が算出したものです。
「1人前あたり」の値を、材料重量の合計で割って可食部100gあたりに換算しています。

## 親子丼

- 1人前(材料重量合計502g): 665kcal / たんぱく質28.5g / 脂質8.9g / 炭水化物110.7g / 食塩相当量2.1g / 野菜量65.0g
- 可食部100gあたり: 132.5kcal / たんぱく質5.7g / 脂質1.8g / 炭水化物22.1g / 食塩相当量0.4g

材料: めし・精白米（水稲） 260g / 若鶏・もも、皮なし＿生 75g / 清酒・上撰 3.75g / たまねぎ・りん茎＿生 60g / かつおだし 25g / こいくちしょうゆ 12g / みりん風調味料 9g / 車糖・上白糖 2.25g / 鶏卵・全卵＿生 50g / 切りみつば・葉＿生 5g
```

### 実行時の検証

スクリプトは出力後に以下を検証し、いずれかに該当したら警告を標準エラーに出す。

- 品目数が250件未満(パース位置のずれを検知するため。実測286件)
- 材料重量の合計が0の行がある(ゼロ除算を避けてスキップした件数。実測0件)
- kcalが0未満、または1000を超える品目(実測範囲内に収まることを確認済みだが、将来のデータ更新に備える)

## アプリ側の変更

### データモデルの変更

`foods`ストアに`kurumeId`を追加する(久留米市データ由来の品目のみ、成分表の`mextCode`と同じ考え方)。

```
foods (食品マスタ)
  - id
  - name
  - category
  - per100g: { kcal, protein, fat, carb, salt }
  - source: "custom"        ※久留米市由来・成分表由来・手入力を問わず custom
  - mextCode: "01088"       ※成分表由来の場合のみ
  - kurumeId: "K011"        ※久留米市データ由来の場合のみ
```

DBバージョンの変更は不要。IndexedDBはレコードごとにスキーマを強制しないため、新しい任意フィールドの追加にマイグレーションは要らない([js/db.js](../../../js/db.js)の`DB_VERSION`はTask3で導入した2のまま)。

### 料理データの読み込み(js/dishTable.js・新規)

[js/mextTable.js](../../../js/mextTable.js)と同じ構造で実装する。

```
loadDishTable(): Promise<Dish[]>
  data/kurume-dishes.json を fetch する。2回目以降はメモリ上のキャッシュを返す。
  食品管理画面の「料理から探す」欄を初めて使ったときに呼ばれる(起動時には読まない)。

searchDishes(table, query, limit = 50): Dish[]
  料理名の部分一致で検索する。空クエリでは空配列を返す。
  前方一致する品目を先に、それ以外を後に並べ、limit件で打ち切る。
```

`js/mextTable.js`の`loadMextTable`/`searchMextFoods`とロジックはほぼ同じだが、別ファイル・別関数として実装する。データソースが異なり(将来どちらかだけ差し替わる可能性がある)、それぞれ独立してテスト・変更できる方が扱いやすいと判断した。

### 食品管理画面(js/foodForm.js)

既存の「成分表から探す」セクションの下に、同じ見た目で「料理から探す」セクションを追加する。

```
┌─ 成分表から探す ────────────────┐
│ (既存のまま)                             │
└────────────────────────────┘
┌─ 料理から探す ──────────────────┐
│ [検索ボックス]                          │
│ ・親子丼                     ごはん / 133kcal │
│ ・かけうどん                  麺 / 92kcal    │
└────────────────────────────┘
┌─ 食品の登録・編集 ──────────────┐
│ (既存のまま)                             │
└────────────────────────────┘
```

候補をクリックすると、その料理の名称とper100g換算済みの栄養値が登録フォームに流し込まれ、食品名欄にフォーカスが移り全選択される(成分表の候補選択と同じ挙動)。`kurumeId`は隠しフィールドとして保持し、保存時に一緒に書き込む。

「成分表から探す」と「料理から探す」は独立した検索欄・候補一覧を持つ。生の食材と完成した料理は探すときの考え方が違う(「豚肉」を探すのか「しょうが焼き」を探すのか)ため、1つの検索欄に混ぜず分けることで、どちらを探しているか迷わないようにする。

初回の検索時に`loadDishTable()`が走るため、読み込み中は候補リストに「料理データを読み込んでいます...」を表示し、失敗時は「料理データの読み込みに失敗しました」を表示する(成分表と同じパターン)。

### Service Worker(sw.js)

- `ASSETS`に`./data/kurume-dishes.json`と`./js/dishTable.js`を追加する
- `CACHE_NAME`を`calorie-app-v3`から`calorie-app-v4`に更新する

## 主要な操作フロー

**久留米市データから料理を登録する**

1. 下部ナビの「食品」をタップ → 食品管理画面
2. 「料理から探す」に「親子丼」と入力
3. 候補「親子丼(ごはん / 133kcal)」をタップ
4. 登録フォームに名称と栄養値(132.5kcal / 5.7 / 1.8 / 22.1 / 0.4)が入り、名前が全選択される
5. そのまま、または名前を打ち替えて「保存」→ 登録済み一覧に「親子丼」が追加される
6. 以降、食事記録モーダルで「親子丼」と入力すると候補に出る

## エラーハンドリング

| 状況 | 挙動 |
|---|---|
| `kurume-dishes.json`の取得失敗 | 候補欄に「料理データの読み込みに失敗しました」を表示。手入力・成分表検索での登録は引き続き可能 |
| 料理検索が0件 | 「該当する料理がありません」を表示 |
| 変換スクリプトで材料重量の合計が0の行を検出 | その行をスキップし、警告件数を標準エラーに出す(通常は0件) |

## テスト方針

既存方針([2026-08-08-mext-food-database-design.md](2026-08-08-mext-food-database-design.md)と同じ)を踏襲する。

**Python側**(`tools/test_build_dish_database.py`、`python -m unittest`で実行)

- per100g換算: 通常ケース(親子丼)、材料重量合計が0のケース(スキップされること)、丸め処理
- CSVの1行を辞書的な構造にパースする関数の単体テスト(材料の空欄をスキップすること、料理名が空の行(あれば)を無視すること)

**JavaScript側**(`tests/dishTable.test.js`、`node --test`で実行)

- `searchDishes`: 空クエリ、部分一致、前方一致の優先、limitでの打ち切り、該当なし(`tests/mextTable.test.js`と同等の観点)

**手動確認**

- 「料理から探す」で「親子丼」を検索→候補選択→フォームに反映→保存→登録済み一覧に表示
- 「成分表から探す」と「料理から探す」が独立して動作すること(片方の検索状態がもう片方に影響しないこと)
- 該当なしのメッセージが出ること
- オフラインで「料理から探す」の検索ができること(Service Workerキャッシュの確認)
